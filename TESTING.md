# Ручное тестирование CYBERПОЛКА

Все команды выполняются из папки `c:\portfolio\polka`.

## Каталог и характеристики (пакет C1)

`npm test` проверяет разбор фильтров, цены, лицензии, ограничения и доступ к
характеристикам в изоляции от БД. Браузерные проверки формы и адресов:
`npx playwright test e2e/catalog-filters.spec.ts`. Они не требуют записей товаров,
но не подтверждают правильность выдачи из настоящей базы. Для проверки данных
нужны применённые миграции, `ydb:test` и авторизованный сценарий публикации/покупки.
Результаты и оставшаяся работа: [PACKAGE_C_CATALOG.md](docs/PACKAGE_C_CATALOG.md).

## Общий кабинет и профиль (пакет B2)

До проверок с данными применить добавочные миграции нужного провайдера, включая
`DeveloperProfile`. Состояние проверок и ограничения окружения описаны в
[PACKAGE_B_PROFILES.md](docs/PACKAGE_B_PROFILES.md).

Изолированные проверки без БД: `npm test`, `npm run ydb:schema:check`.
Гостевой браузерный сценарий: `npx playwright test e2e/account-profile.spec.ts --grep "гость"`.
Для авторизованных сценариев в выделенном окружении с тестовыми аккаунтами:

```powershell
$env:E2E_ACCOUNT_DATABASE = "1"
npx playwright test e2e/account-profile.spec.ts
```

Тесты используют `buyer@polka.test` и `dev@polka.test`; адреса/пароли можно задать
через `E2E_TEST_EMAIL`, `E2E_TEST_PASS`, `E2E_DEVELOPER_EMAIL`, `E2E_DEVELOPER_PASS`.
Авторизованные сценарии проверяют чтение кабинета и редактора, не меняют роли или профиль.

## База данных (Docker Postgres)

База работает в Docker-контейнере `polka-db-1` на порту **5432** (база `polka_db`,
пользователь `polka`, пароль `password`). Подключение задано в `.env.local`.

### Запустить базу

```powershell
docker compose up -d db
```

Данные сохраняются в Docker-томе `polka_pgdata` между перезапусками. После перезагрузки
компьютера Docker Desktop обычно поднимает контейнер сам; если нет — повторите команду.

### Остановить / удалить базу

```powershell
docker compose stop db        # остановить (данные сохранятся)
docker compose down           # удалить контейнер (том с данными останется)
docker compose down -v        # удалить контейнер И все данные
```

### Проверить, что база жива

```powershell
docker exec polka-db-1 pg_isready -U polka -d polka_db
```

## Первичная настройка (один раз / после изменения схемы)

### 1. Сгенерировать клиент Prisma (после изменений `schema.prisma`)

```powershell
npx prisma generate
```

### 2. Накатить схему на базу

Для существующей БД, созданной через `db push`, сначала выполнить проверку и baseline
по [инструкции миграций](docs/DATABASE_MIGRATIONS.md). Пустая база создаётся миграциями.

```powershell
npm run db:deploy
```

### 3. Засеять тестовые данные

Скрипты сами читают `.env.local`, ручной `DATABASE_URL` указывать не нужно.

```powershell
npm run db:seed:demo                   # 6 демо-продуктов + демо-автор (dev-only)
npx tsx scripts/seed-test-users.ts     # 4 тестовых аккаунта (см. таблицу выше)
```

## Запуск приложения

```powershell
npm run dev
```

Приложение доступно на **http://localhost:3000**

Остановить — `Ctrl+C` в терминале. Если сервер запущен в фоне и порт занят
(или после нескольких перезапусков накопились «осиротевшие» процессы, из-за которых
все маршруты отдают 500 и в логе `Another write batch ... already active`):

```powershell
# убить всё, что слушает :3000, и все node-процессы next dev
Get-NetTCPConnection -LocalPort 3000 -State Listen | Select -Expand OwningProcess -Unique |
  ForEach-Object { Stop-Process -Id $_ -Force }
Get-CimInstance Win32_Process -Filter "Name='node.exe'" |
  Where-Object { $_.CommandLine -match 'next' -and $_.CommandLine -match 'dev' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
Remove-Item .next -Recurse -Force    # затем чистый старт
```

> Если при старте Turbopack ругается на повреждённый кэш (`corrupted database`,
> `Failed to restore task data`) — удалите кэш и запустите снова:
> ```powershell
> Remove-Item .next -Recurse -Force
> npm run dev
> ```

## Что тестировать

### Покупатель (`buyer@polka.test`)
- `/login` — вход
- `/catalog` — каталог, фильтры по категориям, поиск, сортировка
- `/product/<slug>` — страница продукта: описание, требования, «что входит», покупка, Q&A
  (в вопросе нельзя оставить телефон/email/телеграм — сработает фильтр контактов)
- `/sell` под покупателем — кнопка «Стать разработчиком»: роль меняется на месте,
  без пере-логина, и открывается кабинет разработчика
- `/purchases` — история покупок (бейдж непрочитанных сообщений)
- `/purchases/<id>` — детали покупки: скачивание, инструкция, переписка с разработчиком
  (в чате тоже действует фильтр контактов)
- `/purchases/<id>/download` — страница скачивания: инструктаж по безопасности + согласие;
  для снятого продукта — блок с ⚠ вместо кнопки
- Бейдж сообщений (иконка письма) в шапке — счётчик непрочитанных

### Разработчик (`dev@polka.test`)
- `/dashboard` — баланс, продажи, слоты
- `/dashboard/products` — список своих продуктов
- `/submit` — загрузка нового продукта (мастер: категория → описание → функции →
  установка → медиа → цена)
- `/dashboard/payouts` — запрос вывода средств
- `/dashboard/questions` — ответы на вопросы покупателей по своим продуктам
- `/dashboard/messages` — диалоги с покупателями; `/dashboard/messages/<id>` — тред
- `/sell` — лендинг для разработчиков, калькулятор дохода

### Модератор (`moderator@polka.test`)
- `/admin/queue` — очередь продуктов на проверку
- `/admin/review/<id>` — карточка проверки: скан, авто-оценка, инструкция, находки
  дубликатов (ссылка на оригинал); кнопка «Подтвердить работоспособность»; одобрить / отклонить;
  снятие с публикации и «Информировать покупателей о проблеме безопасности»
- `/admin/products` — все продукты с поиском и фильтром по статусу; быстрое снятие/восстановление

Бейдж «Проверено вручную» после подтверждения виден на странице продукта, в каталоге
и даёт буст в сортировке «Популярные». При одобрении новой версии бейдж снимается.

### Администратор (`admin@polka.test`)
- Всё из списков выше
- `/admin/users`, `/admin/coupons`

### Публичные страницы
- `/` — лендинг (Hero, цифры, популярное, категории, безопасность)
- `/sell` — страница для разработчиков

## Автоматические тесты

`npm test` проверяет серверные исходники с изолированными БД и сетевыми зависимостями:
повторные платежи, откат при ошибке, отзыв JWT, одноразовый reset-токен, защищённые
копии файлов и ошибки анализатора. Эти проверки не заменяют интеграционные тесты PostgreSQL/S3/эквайринга.

На 11 ноября 2026 года проходят 194 проверки, включая восстановление загрузки,
потерянные ответы, параллельное создание черновика/заявки, отзыв и запрет новой
ссылки после смены статуса покупки. Подробности и ограничения — в
[пакете C2](docs/PACKAGE_C_PUBLICATION.md) и
[пакете C3](docs/PACKAGE_C_FINANCES.md). C3 добавляет конкурирующие выплаты/возвраты,
удержания, неизвестные результаты провайдеров и обработку чеков.
Транзакционные фикстуры работают в памяти;
настоящая изоляция PostgreSQL/YDB и банковские возвраты ими не подтверждаются.
Пакет [D1](docs/PACKAGE_D_ORDERS.md) добавляет полный цикл заказа, приватность
предложений/файлов/переписки, конкурирующие выбор/приёмку, споры и именованные
связи YDB. Старые обращения не публикуются и не используются как тестовые заказы.

Пакет [E1](docs/PACKAGE_E_DEVELOPERS.md) добавляет добровольное участие в каталоге,
ротацию всей выборки, приватность карточек, ограничения и повторы приглашений,
согласие на аналитику, подписанные события, их очистку и сводные группы опыта.
Это 21 новая изолированная проверка; настоящий SQL и борьба с мультиаккаунтами
ими не подтверждаются.

На подготовленном локальном production-сервере можно повторить 25 проверок
публичного интерфейса и гостевых запретов без создания аккаунтов или записей в БД:

```powershell
$env:CI = "1"
$env:PLAYWRIGHT_BASE_URL = "http://127.0.0.1:3100"
npx playwright test e2e/public-presentation.spec.ts e2e/account-profile.spec.ts e2e/catalog-filters.spec.ts e2e/store-boundaries.spec.ts e2e/financial-boundaries.spec.ts e2e/orders.spec.ts e2e/developers.spec.ts --grep-invert "Кабинет и профиль с тестовой БД" --workers=1 --retries=0
```

Без доступной БД эти сценарии проверяют интерфейс/ошибки доступа, а не реальные
результаты каталога или авторизованную покупку. Отдельная компонентная проверка
мастера/дозагрузки использовала подставленные API; снимки находятся в
`test-screenshots/package-c2/`. Компоненты возврата и чека также проверены с
подставленными API; снимки — `test-screenshots/package-c3/`.
Компоненты биржи прошли полный путь с настоящей серверной логикой и БД/S3
в памяти; смена ролей стенда не является реальным входом. Снимки —
`test-screenshots/package-d1/`. Настоящие SQL, закрытый бакет и доставка уведомлений
проверяются отдельно после применения новых миграций YDB.
Компоненты каталога/профиля/приглашений E1 проверены в браузере с настоящими
обработчиками и БД в памяти: согласие, видимый показ, исключение повторов при
перезагрузке, открытие профиля, приглашение и выключение участия. Проверены ширины
320/375/768/1440; снимки — `test-screenshots/package-e1/`. Подстановка пользователя
на этом стенде не является проверкой настоящего входа, email или Telegram.
Скрипт `ydb:test` содержит дополнительные проверки
на синтетических данных и изменяет тестовую БД; его полный запуск ещё предстоит
после миграций 002–007. 11 ноября отдельно прошли 11 базовых проверок настоящей YDB
через `scripts/ydb/verify.ts --write-probe`; [результаты](docs/YDB_VERIFICATION_2026_11_11.md).
Для настоящего контрольного пути нужны тестовые аккаунты, S3,
сканеры и согласованный сценарий оплаты/возврата/выплаты.

Playwright-сценарии успешного входа требуют тестовых пользователей из раздела выше.
Неверные учётные данные теперь приводят к ошибке теста. Создание нового аккаунта
включается только через `E2E_ALLOW_REGISTRATION=1` в выделенном тестовом окружении;
при необходимости указать `E2E_REGISTRATION_DOMAIN`, разрешённый для регистрации.
Отключить CAPTCHA для такого автоматизированного окружения. Тест регистрации
создаёт уникальный аккаунт и не должен запускаться на рабочей БД.

```powershell
npm run test:e2e          # Playwright e2e (нужен запущенный dev-сервер на :3000)
npm test                 # изолированные регрессионные проверки безопасности
npx tsx test-zip-bomb.ts  # юнит-тесты защиты от zip-бомб
node test-run.mjs         # браузерный смоук-тест (нужен запущенный dev-сервер)
```
