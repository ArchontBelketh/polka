## Параметры базы

Параметры, полученные из консоли 10 ноября 2026 года, сохранены в локальном `.env.local`:

```dotenv
YDB_ENDPOINT="grpcs://ydb.serverless.yandexcloud.net:2135"
YDB_DATABASE="/ru-central1/b1gni48t35djievutl9m/etnq8n4vu37vo2bgd8uv"
YDB_SERVICE_ACCOUNT_KEY_FILE=".secrets/authorized_key.json"
```

`YDB_ENDPOINT` содержит только адрес сервера. Часть после `/?database=` из строки
консоли записывается отдельно в `YDB_DATABASE`.
`YDB_SERVICE_ACCOUNT_KEY_FILE` — настройка нашего проверочного скрипта, а не стандартная
переменная авторизации всех YDB SDK. `DATABASE_URL` пока остаётся адресом PostgreSQL.

## Сервисный аккаунт и ключ

1. Выберите каталог с базой в консоли Yandex Cloud. Откройте **Identity and Access
   Management → Сервисные аккаунты → Создать сервисный аккаунт**.
2. Имя: `cyberpolka-ydb-dev`. Создайте аккаунт без ролей на всё облако или каталог.
3. Откройте нужную базу в **Managed Service for YDB → Права доступа**. Добавьте
   созданный сервисный аккаунт с ролью **`ydb.editor` на эту базу**. Это доступ для
   разработки: чтение, запись и изменение схемы. Роль также даёт управление самой
   базой; для рабочего приложения права нужно отдельно сузить под его запросы.
4. Вернитесь в сервисный аккаунт: **Создать новый ключ → Создать авторизованный ключ**.
   Оставьте стандартный алгоритм и скачайте файл с ключами в формате JSON.
   Ключи Object Storage и API-ключи для этого способа подключения не подходят.
5. Сохраните JSON как `C:\portfolio\polka\.secrets\authorized_key.json` и укажите
   этот путь в `YDB_SERVICE_ACCOUNT_KEY_FILE`. Можно использовать другое имя файла,
   если переменная указывает на него.
   Передавать его содержимое в чат не требуется.

Папка `.secrets/` исключена из Git, Docker-контекста, архива `make-release.sh`
и синхронизации `deploy.sh`. Для других способов упаковки её нужно также исключить.

## Проверка соединения

Установите YDB CLI по [официальной инструкции для Windows](https://ydb.tech/docs/en/reference/ydb-cli/install).
Откройте новый PowerShell и проверьте установку:

```powershell
ydb version
```

Если CLI установлен вне PATH, укажите полный путь к `ydb.exe` в `YDB_CLI_PATH`
в `.env.local`, используя прямые слеши, например `C:/tools/ydb.exe`.

Для текущей локальной проверки CLI скачан из официального хранилища в
`node_modules/.cache/ydb/ydb.exe`; абсолютный путь записан в локальный `YDB_CLI_PATH`.
Установка не меняет системный PATH. Этот кеш может быть удалён при переустановке
зависимостей; в таком случае установите CLI заново и обновите путь.

Из корня проекта:

```powershell
npm run ydb:check
```

Скрипт использует локальные настройки и авторизованный JSON-ключ, выполняет
`SELECT 1 AS connection_ok;` с лимитом времени 60 секунд. Успех: таблица с
`connection_ok = 1` и сообщение об успешной проверке. Таблицы и данные не изменяются.
Проверка подтверждает подключение и выполнение запроса, но не права на запись.

Расширенная проверка без изменения данных: `npx tsx scripts/ydb/verify.ts`.
Чтобы дополнительно проверить запись, откат и конкуренцию на случайных
диагностических ключах: `npx tsx scripts/ydb/verify.ts --write-probe`.
После неё скрипт удаляет только свои строки и проверяет результат очистки.

При ошибке доступа проверьте роль **на нужной базе**, а также что ключ выпущен именно
для выбранного сервисного аккаунта. При сетевой ошибке проверьте доступность
`ydb.serverless.yandexcloud.net:2135`. Ошибка авторизации до выполнения запроса может
также означать недоступность `iam.api.cloud.yandex.net:443` для обмена ключа на IAM-токен.

## Следующий этап

Подготовлен нативный слой операций проекта на `ydb-sdk@5.11.1`: фильтры,
связанные выборки, счётчики, агрегации, запись и транзакции. Существующие вызовы
используют сгенерированные типы Prisma как контракт; Prisma не подключается к YDB
и не выполняет её запросы. Неизвестные операции отклоняются явно.
SQL и значения передаются раздельно; имена таблиц и полей берутся из проверенной схемы.
Деньги и счётчики изменяются в сериализуемых транзакциях; повторяется весь блок
только при подтверждённом `ABORTED`. Неопределённый результат коммита не повторяется.

Уникальность обеспечивается записями `_UniqueValue` в той же транзакции,
внешние ключи и каскады — кодом слоя данных. Прямые SQL/BulkUpsert записи в
бизнес-таблицы обходят эти проверки: импорт данных должен проходить через адаптер
или отдельно воспроизводить его ограничения и уникальные ключи.
JSON и массивы хранятся как `JsonDocument`, даты — `Timestamp`, суммы — `Int32` в копейках.
Постраничное чтение не принимает обрезанные ответы YDB за полные результаты.
Сложные выборки могут создавать дополнительные запросы к связанным таблицам;
производительность и реальная семантика должны быть проверены интеграционно.

Команды подготовки и проверки:

```powershell
npm run ydb:generate       # обновить метаданные по prisma/schema.prisma
npm run ydb:schema:check   # метаданные и неизменяемые снимки миграций, без сети
npm run ydb:migrate        # последовательные миграции, проверка схемы, без пересоздания
npm run ydb:check:sdk      # соединение через SDK, SELECT 1
npm run ydb:test           # реальные запросы и транзакции с синтетическими данными
npm test                  # изолированные регрессионные тесты
```

Мигратор использует API таблиц и журнал `APPLYING`/`APPLIED`; после прерывания можно
повторить запуск с той же схемой. Неизвестные существующие бизнес-таблицы и несовпадающий
baseline не принимаются автоматически. Схемные операции ограничены по частоте.
Текущий baseline — начальный снимок; дальнейшие изменения требуют явных новых миграций.
Readiness текущего кода требует применённые `001_baseline`, `002_developer_profile`,
`003_product_specification`, `004_product_uploads`, `005_financial_operations`
`006_job_marketplace` и `007_developer_directory`,
с совпадающими хешами.
Миграции запускать одним процессом до обновления приложения. Проверить их на выделенном
окружении и восстановленном снимке до переноса рабочего сайта.

Базовые SQL-проверки 11 ноября прошли. Следующий отдельный этап — проверить и применить подготовленные
миграции в тестовом окружении, затем выполнить `ydb:test`, проверить вход,
регистрацию, восстановление пароля, каталог, покупку и админку локального сайта.
Только после этого включать `DB_PROVIDER="ydb"` в `.env.local` и переносить реальные данные.
Пока локальные настройки приложения сохраняют PostgreSQL по умолчанию.
Проверка готовности приложения в режиме YDB читает журнал миграций, а не только `SELECT 1`.
Существующие Prisma-миграции относятся к исходной PostgreSQL-базе.

Рабочая схема: браузер посетителя → существующий сервер Next.js → облачная YDB.
Этот компьютер нужен только для разработки и проверки. Доступ и ключ для
приложения на сервере настраиваются отдельно; локальный Windows CLI и его путь
не переносятся в серверную конфигурацию. Способ авторизации на сервере зависит
от размещения: текущий слой использует авторизованный ключ сервисного аккаунта
или явно переданный краткоживущий IAM-токен. Поддержку метаданных для ресурсов
Yandex Cloud при необходимости подключаем отдельно.
Доступ к серверу и его размещение ещё не уточнены. Исходную PostgreSQL-базу
сохраняем до переноса, проверки данных и переключения приложения.

Подготовлен `docker-compose.ydb.yml` для репетиции запуска с YDB: приложение и
мигратор получают JSON-ключ через read-only Docker secret, PostgreSQL в этой
конфигурации не запускается. На сервере следует задать Linux-путь ключа через
секрет; локальный `YDB_CLI_PATH` переносить не нужно. Docker-конфигурация прошла
проверку синтаксиса, сборка Docker-образов и запуск на сервере не выполнялись.
Скрипты администратора и демо-данных используют выбранный `DB_PROVIDER`;
`npm run db:deploy` выбирает мигратор по этому же параметру.

Остаются до переноса рабочего сайта: выгрузка согласованного снимка PostgreSQL,
проверяемый импорт с сохранением ID/хешей паролей/балансов, сверка количества и
связей записей, проверка основных сценариев и настройка серверного окружения.
Реальные данные и настройки рабочего сервера в этой сессии не менялись.
