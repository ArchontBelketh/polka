# Миграции существующей Киберполки

Приложение использует Prisma Migrate. `prisma/migrations/0_baseline` фиксирует схему из репозитория до первого пакета исправлений. Следующая миграция добавляет `User.sessionVersion` для отзыва сессий. Baseline получен из локального исходного кода, а не из проверенного снимка продакшен-БД.

## Новая пустая база

```powershell
npm run db:deploy
npm run db:generate
```

В Docker: `docker compose -f docker-compose.yml -f docker-compose.prod.yml run --rm migrate`.

## Существующая база, ранее управляемая через db push

1. Сделать резервную копию и проверить восстановление на отдельной базе.
2. Проверить фактическую схему до применения новой миграции:

   ```powershell
   npm run db:baseline:check
   ```

   Команда только сравнивает схему. Код завершения 0 — совпадение, 2 — расхождение, 1 — ошибка проверки. При расхождении проверить SQL diff и согласовать исправление. При ошибке доступа проверка не считается пройденной.

3. Только после успешного сравнения отметить исходную схему как уже существующую:

   ```powershell
   npx prisma migrate resolve --applied 0_baseline
   ```

4. Применить добавочные миграции, затем обновить приложение:

   ```powershell
   npm run db:deploy
   npm run db:generate
   ```

Для Docker сравнение выполняется в том же окружении, что и миграции:

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml build migrate
docker compose -f docker-compose.yml -f docker-compose.prod.yml run --rm migrate npx prisma migrate diff --from-config-datasource --to-schema prisma/migrations/0_baseline/schema.prisma --exit-code
# Только после совпадения, резервной копии и проверенного восстановления:
docker compose -f docker-compose.yml -f docker-compose.prod.yml run --rm migrate npx prisma migrate resolve --applied 0_baseline
docker compose -f docker-compose.yml -f docker-compose.prod.yml run --rm migrate
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d app
```

Не выполнять `migrate reset`, не применять baseline SQL повторно к существующим таблицам и не отмечать добавочную миграцию как выполненную без её применения. Если уже есть другая история Prisma Migrate, сначала сопоставить её с новой историей; не разрешать конфликт автоматическим `resolve`.

## Последующие изменения

Пакет B2 добавляет `20261110000200_developer_profile` для PostgreSQL; она должна
быть применена до запуска новых страниц профиля. Исходные пользователи и данные
магазина не переносятся и не перезаписываются этой миграцией. Схема валидна,
но исполнение SQL на настоящей PostgreSQL в текущем окружении не проверялось.
Для YDB используется отдельная последовательность нативных миграций:
неизменный `001_baseline` и новая `002_developer_profile`, см. [YDB_SETUP.md](YDB_SETUP.md).

Пакет C1 добавляет `20261110000300_product_specification` для PostgreSQL
и `003_product_specification` для YDB. Это новая необязательная таблица по ID товара;
существующие товары и лицензии не переписываются. Метаданные кода содержат 35 моделей.
Миграции подготовлены локально; выполнение на настоящих базах и проверка старых
покупок после обновления ещё предстоят. Подробности: [PACKAGE_C_CATALOG.md](PACKAGE_C_CATALOG.md).

Пакет C2 добавляет `20261110000400_product_uploads` для PostgreSQL
и `004_product_uploads` для YDB: `ProductSubmission`, `ProductUpload` и enum
статусов загрузки. Схема теперь содержит 37 моделей. Миграции создают новые
таблицы/индексы/связи без переписывания существующих товаров и покупок.
Prisma validate/generate и локальное сравнение схем прошли; исполнение SQL
на настоящей БД не проверялось. Облачная YDB остаётся на 33 исходных моделях,
002–004 ещё не применялись. До выпуска нового мастера и API применить добавочные
миграции выбранного провайдера в тестовом окружении и проверить восстановленный
снимок. Подробности: [PACKAGE_C_PUBLICATION.md](PACKAGE_C_PUBLICATION.md).

Пакет C3 добавляет `20261110000500_financial_operations` для PostgreSQL
и `005_financial_operations` для YDB: таблица журнала, enum статусов и индексы.
Всего 38 моделей, пять снимков YDB. Исторические балансы и выплаты не переписываются.
SQL сопоставлен с локальным сравнением Prisma, на настоящей БД не исполнялся.
Облачная YDB остаётся на исходных 33 моделях; 002–005 не применены.
При выпуске остановить прежние финансовые обработчики и cron до переключения
версии: старый код не использует журнал и новые блокировки.
Подробности и порядок сверки: [PACKAGE_C_FINANCES.md](PACKAGE_C_FINANCES.md).

Пакет D1 добавляет `20261110000600_job_marketplace` для PostgreSQL
и `006_job_marketplace` для YDB: 10 таблиц биржи, четыре enum, индексы и связи.
Всего 48 моделей и шесть снимков YDB. Старые `Request`/`Executor` не преобразуются;
обратные связи `User`/`SupportTicket` не меняют их физические колонки.
SQL получен локальным сравнением схем, на настоящей БД не исполнялся.
Облачная схема остаётся на исходных 33 моделях; 002–006 не применены.
Сначала проверить добавочные миграции выбранного провайдера на восстановленной
копии, затем выпускать новые API и страницы. Подробности:
[PACKAGE_D_ORDERS.md](PACKAGE_D_ORDERS.md).

Пакет E1 добавляет `20261111000700_developer_directory` для PostgreSQL и
`007_developer_directory` для YDB: три новые таблицы `DeveloperListing`,
`JobInvitation`, `ExposureEvent`, индексы и связи. Итого 51 модель и семь снимков.
SQL получен офлайн сравнением схем и не применялся к настоящей БД. В облаке
002–007 остаются неприменёнными. Существующие профили автоматически в каталог
не включаются; сбор событий по умолчанию выключен. Подробнее:
[PACKAGE_E_DEVELOPERS.md](PACKAGE_E_DEVELOPERS.md).

Создавать миграции на отдельной базе разработки через `prisma migrate dev`, просматривать SQL и сохранять его в репозитории. Продакшен обновлять через `migrate deploy`. `db:push` остаётся вспомогательной командой для одноразовых экспериментов на отдельной базе; штатный запуск и деплой её не используют.

Для каждой миграции проверять прямой запуск на пустой базе и обновление восстановленной существующей базы. Отдельно проверять сохранение старых покупок, версий и прав доступа.

## Особенности первого пакета

- Применить миграцию `sessionVersion` до запуска нового кода авторизации.
- Существующие JWT без версии принимаются как версия 0. После блокировки или смены пароля версия увеличивается; разблокировка старую сессию не восстанавливает.
- Уже выданные ссылки загрузки действуют до истечения прежнего TTL. Новые загрузки используют отдельные staging-ключи, а покупатели получают серверные копии.
- Старые файлы и покупки не удаляются. Новые версии кода направляются на ручную модерацию.
- После миграции проверить вход, смену пароля, блокировку пользователя, покупку и выдачу файла на тестовых аккаунтах.

В текущем окружении Docker daemon и PostgreSQL недоступны. Миграции подготовлены, но к реальной базе не применялись; совпадение baseline с продакшеном и восстановление резервной копии ещё не подтверждены.
