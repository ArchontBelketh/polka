# Пакет C3: возвраты, выплаты и подтверждение чеков

Дата: 10 ноября 2026 года. Продолжение [C2](PACKAGE_C_PUBLICATION.md).
Следующий реализованный пакет: [D1 — цикл заказа биржи](PACKAGE_D_ORDERS.md).
Реализация подготовлена локально; рабочий сервер, банк, касса и облачная схема
не изменялись. Существующие комиссии и способ оплаты сохранены.

## Исправленные сценарии

- Параллельные запросы выплаты резервируют одни продажи и баланс один раз.
  Перед расчётом берётся блокировка строки разработчика, затем перечитываются
  текущие заморозка/блокировка аккаунта, продажи и баланс. Несогласованные суммы,
  открытые претензии и оформляемые возвраты препятствуют новой выплате.
- Отклонение выплаты возвращает резерв и освобождает продажи одной транзакцией.
  Повторный запрос того же статуса не повторяет возврат на баланс. Конкурирующие
  «Выплачено» и «Отклонить» не перезаписывают конечное состояние друг друга.
- Отметка «Выплачено» фиксирует ручной перевод; сайт не отправляет деньги автору.
  Состав чека сохраняется в той же транзакции до обращения к кассе. Открытая
  претензия или возврат по зарезервированной продаже препятствуют подтверждению.
- Cron зачисления удержанных сумм перечитывает покупку, окно удержания,
  начисление, претензию и журнал возвратов под той же блокировкой разработчика.
  Запись `creditedAt` и изменение баланса происходят одной транзакцией.
  Параллельные запуски не должны зачислять продажу дважды.
- Подача претензии также использует эту блокировку: конкурентные запросы
  создают один тикет. Проверяются текущий покупатель, оплаченный статус, окно
  претензии и модель продажи. Уведомление отправляется после коммита.
- Финансовые маршруты проверяют текущего пользователя и роль через
  `getCurrentUser`; публичные ответы не содержат payload журнала или контактов автора.

Эти гарантии проверены на изолированных фикстурах. Поведение блокировок и
транзакций PostgreSQL/YDB ещё требует интеграционной проверки на настоящей БД.

## Журнал внешних операций

Добавлена таблица `FinancialOperation`. Для полного банковского возврата ключ
равен `refund:{purchaseId}`, для расходного чека — `payout-receipt:{payoutId}`.
Журнал хранит инициатора, сумму, снимок необходимых данных, статус провайдера,
его идентификатор и дату применения. Не публиковать его payload пользователям:
снимок расходного чека может содержать email получателя.

| Статус | Значение |
| --- | --- |
| `PREPARED` | Операция подготовлена в БД; отправку ещё можно занять условной записью |
| `IN_FLIGHT` | Право первой отправки занято; результат внешнего обращения может быть неизвестен |
| `UNKNOWN` | Недостаточно подтверждений результата; повторная отправка автоматически запрещена |
| `CONFIRMED` | Для возврата получен `REFUNDED`; для чека сохранён принятый кассой ID |
| `APPLIED` | Локальный учёт возврата применён либо касса подтвердила `Processed` |

Сеть вызывается после завершения транзакции. Неопределённый результат коммита
не является поводом выполнить внешнюю отправку заново. Обработчик, остановившийся
после занятия `IN_FLIGHT` и до отправки, тоже требует сверки, а не автоматического
сброса статуса. Это сознательная граница защиты от повторного внешнего действия.

## Полный банковский возврат

Маршрут: `POST /api/admin/purchases/{id}/refund`, только администратор.

1. В транзакции проверяются историческая сумма покупки, банковский `paymentId`,
   начисление и связанная выплата. Один банковский платёж не должен быть связан
   с несколькими покупками. Незавершённую выплату нужно разобрать до возврата.
   Прямая оплата автору без банковского `paymentId` через этот маршрут не возвращается.
2. Условная запись `PREPARED → IN_FLIGHT` разрешает только одну отправку `Cancel`.
   Перед ней `GetState` проверяет идентификатор, `CONFIRMED` и сумму платежа.
   У обёртки больше нет аргумента «ключ идемпотентности», который раньше игнорировался.
3. Только `REFUNDED` позволяет применить учёт. `REFUNDING`, частичный возврат,
   неизвестный статус, потерянный ответ и неполные данные не считаются завершением.
4. Статус покупки, число продаж, обратное начисление автору, закрытие претензии
   и `APPLIED` записываются одной транзакцией. Если она не завершилась, повтор
   применяет локальный учёт после сверки без нового `Cancel`.

HTTP 200 означает учтённый возврат, HTTP 202 — необходимость дальнейшей сверки.
Админка показывает «Проверить возврат» и сохраняет состояние после обновления страницы.
Повтор с занятой отправкой только запрашивает состояние банка; при `CONFIRMED`
после неизвестного результата новый `Cancel` не выполняется. Нужна ручная сверка
операции в банке. Интерфейса принудительного сброса журнала нет.

Возврат уже выплаченной автору продажи может образовать отрицательный баланс
по существующей модели учёта. Новая выплата не создаётся, если баланс не покрывает
сумму включаемых продаж; автоматические частичные выплаты и новая комиссия не вводились.
Ранее выданные подписанные ссылки скачивания сохраняют свой TTL, как описано в C2.

Основание для обработки полного возврата и статусов:
[Cancel](https://developer.tbank.ru/eacq/api/cancel),
[GetState](https://developer.tbank.ru/eacq/api/get-state) и
[справочник статусов Т-Банка](https://developer.tbank.ru/eacq/intro/developer/operation-statuses).
Реальные вызовы банка в этой сессии не выполнялись.

## Расходный чек

После фиксации выплаты только одна попытка отправляет сохранённый состав чека.
В CloudKassir передаётся стабильный `X-Request-ID`. Пустой/неполный HTTP-ответ
не считается успехом: нужны `Success: true`, ID чека и нулевой `ErrorCode`.
Принятый ID сохраняется, затем проверяется `/kkt/receipt/status/get`.

`Queued` показывает ожидание; только `Processed` выставляет `receiptSent`.
Кнопка «Проверить чек» доступна у выполненной выплаты без подтверждённого чека.
Она проверяет сохранённый ID и не создаёт новый чек. `Error` требует разбора кассы.
При потере ответа с ID повторная автоматическая отправка запрещена: нужно найти
чек по выплате в кабинете кассы и сверить результат вручную.
Для исторических `PAID` без журнала чек автоматически не отправляется.

Провайдер хранит результат дедупликации лишь один час, поэтому один заголовок
не заменяет долговременный журнал. Создание чека асинхронно; приём в очередь
не равен фискализации. Источник: [API CloudKassir](https://developers.cloudkassir.ru/).
Юридическая корректность состава/типов чеков и договорная схема этим техническим
изменением не подтверждаются; они остаются частью проверки расчётной модели.

## Миграции и выпуск

PostgreSQL: `20261110000500_financial_operations`.
YDB: `005_financial_operations`. Схема содержит 38 моделей и пять неизменяемых
снимков YDB. Добавляются таблица, enum и индексы, без изменения существующих
покупок, выплат и балансов. SQL сопоставлен с локальным `prisma migrate diff`.
На настоящих базах миграция не исполнялась; облачная YDB по последней проверке
остаётся на исходных 33 бизнес-таблицах, 002–005 ещё не применены.

Перед выпуском проверить миграции выбранного провайдера на восстановленной копии.
Остановить старые финансовые обработчики/cron на время переключения версии:
экземпляры прежнего кода не используют новый журнал и общие блокировки.
Применить миграции до запуска новых API/админки, затем проверить сохранность
покупок, балансов и резервов. Рабочий сервер и реальные расчёты здесь не менялись.

## Проверки

- 141 регрессионный тест проходит, в том числе 30 новых: конкурирующие выплаты,
  отклонения и cron, повторный возврат, потеря ответа, откат локального учёта,
  задолженность после выплаты, неполные ответы провайдеров, очередь чека,
  повторная сверка, приватность и права доступа.
- 17 браузерных сценариев публичного интерфейса и гостевых запретов проходят
  на production-сборке; три новых закрывают финансовые маршруты для гостей.
- Компоненты админки проверены с подставленными API: 202 не показывает завершённый
  возврат, повтор выполняет сверку, очередь чека сохраняет предупреждение,
  конечный статус не предлагает отклонение. Ширины 320/375/768/1440 px проверены
  без переполнения и ошибок JavaScript. Снимки: `test-screenshots/package-c3/`.
- Production-сборка с TypeScript, Prisma validate/generate, локальное сравнение
  схем и `ydb:schema:check` проходят. Изолированная БД в тестах не доказывает
  поведение реальных SQL-транзакций. Docker-образ не собирался.
- В `ydb:test` подготовлены нативные проверки резерва/отклонения выплаты и отката
  журнала на синтетических данных, без банковских переводов или чеков.
  Они не запускались из-за ранее подтверждённого таймаута SQL YDB.

Пакет C остаётся открытым до контрольной покупки, выдачи настоящего файла,
проверки возврата и учёта выплаты в подходящем окружении. Далее по плану можно
готовить модель заказов биржи (пакет D); переключение на YDB и проверка реальных
расчётов требуют устранения облачного таймаута и отдельной репетиции переноса.
