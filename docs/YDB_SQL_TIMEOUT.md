# Диагностика таймаута SQL в YDB

**Обновление 11 ноября 2026:** прежняя ошибка в повторной проверке не воспроизвелась.
SDK и CLI читают таблицы; запись, откат и два параллельных обновления прошли.
[Результаты и границы проверки](YDB_VERIFICATION_2026_11_11.md).
Ниже — история первоначального сбоя; его причина осталась неизвестной.

Дата: 10 ноября 2026 года. Проблема воспроизведена с локального компьютера и
в редакторе запросов консоли Yandex Cloud. Причина пока не установлена.

## Проверенные факты

- База `etnq8n4vu37vo2bgd8uv`, каталог `b1gni48t35djievutl9m`, статус `RUNNING`.
- Endpoint: `grpcs://ydb.serverless.yandexcloud.net:2135`.
- Путь: `/ru-central1/b1gni48t35djievutl9m/etnq8n4vu37vo2bgd8uv`.
- Serverless: включён лимит **10 RU/с**; выделенная мощность не включена.
- CLI 2.35.0 и нативный SDK 5.11.1 успешно выполняют `SELECT 1`.
- API таблиц успешно создаёт таблицы, возвращает их схему, читает и записывает
  журнал миграций (`ReadTable` / `BulkUpsert`). Созданы все 33 бизнес-таблицы.
- SQL-чтение таблиц получает таймаут. Явный `PRAGMA TablePathPrefix` результата не изменил.
- Пользователь проверил тот же запрос в консоли и получил `GRpc error: (4): Deadline Exceeded`.

Запрос для воспроизведения к пустой диагностической таблице:

```sql
SELECT * FROM `CyberPolkaConnectionProbe` LIMIT 1;
```

Также воспроизводится на SQL-чтении `_SchemaMigration` и `User`.
Повторная проверка при подготовке C2 запросом `SELECT COUNT(*) AS probe_count FROM
CyberPolkaConnectionProbe;` также завершилась таймаутом, native status `400090`.
Это была проверка только чтением, без применения новых миграций или изменения лимита.
Ответ SDK:

```text
Timeout (code 400090)
Request timeout 10000ms exceeded
Cancelling after 10000ms during compilation
```

Таблица `CyberPolkaConnectionProbe` создана отдельно для диагностики, не содержит
пользовательских данных и пока сохранена для воспроизведения ошибки.
JSON-ключ и токены к диагностике прикладывать не нужно.

## После восстановления SQL

1. Повторить запрос в консоли. Проверить `npm run ydb:schema:check`, применить
   подготовленные миграции B2/C1/C2/C3/D1/E1 (002–007) в тестовом окружении, затем выполнить `npm run ydb:test`.
2. Исправить и проверить обнаруженные различия запросов/транзакций адаптера,
   включая фильтры по языку, платформе и совместимости товара, повторное создание
   черновика, журнал загрузок, параллельные заявки покупки/отзывы, резерв выплат
   и откат финансового журнала. Настоящие банк и касса в `ydb:test` не вызываются.
   Проверки D1 добавляют нативный цикл заказа, именованные связи, конкурентный
   выбор исполнителя, приёмку и отзывы; хранилище и уведомления также не вызываются.
   E1 дополняет проверки каталогом разработчиков и параллельными приглашениями.
3. Выполнить сценарии приложения локально с YDB, затем подготовить перенос данных.
4. После успешных проверок удалить только диагностическую таблицу и готовить серверный запуск.

Источник для проверки настроек: [Database.Get API](https://yandex.cloud/ru/docs/ydb/api-ref/Database/get).
