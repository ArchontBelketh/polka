# Временные загрузки товаров

Новый протокол исходников и скриншотов описан в [пакете C2](PACKAGE_C_PUBLICATION.md).
Ниже — обслуживание объектов, без изменения действующего бакета в этой сессии.

## Пути и сроки

| Назначение | Префикс | Кто записывает |
| --- | --- | --- |
| Временный исходник/скриншот | `staging/products/{id}/source/` или `screenshot/` | Клиент по подписанному PUT |
| Подтверждённый исходник | `products/{id}/artifacts/{sha256}/` | Сервер |
| Подтверждённое изображение | `products/{id}/images/{sha256}/` | Сервер |
| Загрузка новой версии, прежний протокол | `products/{id}/uploads/version/` | Клиент по подписанному PUT |

Для постоянных копий сервер никогда не выдаёт клиенту PUT. Старые файлы и
версионные пути не входят в область новой очистки `staging/`.
Подписанная ссылка загрузки действует 15 минут; подтверждённая копия сохраняется
отдельно. При неизвестном результате коммита копия остаётся для последующей сверки.

## Очистка по журналу попыток

```powershell
npm run uploads:cleanup                 # только подсчёт кандидатов, без удаления
npm run uploads:cleanup -- --help        # справка, без соединения с БД
npm run uploads:cleanup -- --apply       # выполнить удаление временных объектов
```

Команда использует текущий `DB_PROVIDER` и серверные настройки Object Storage.
За проход выбирает до 100 записей без `stagingDeletedAt`: старше 24 часов с момента
обновления или уже отменённые. Вывод содержит только счётчики, без ключей файлов.
Перед `--apply` проверить окружение, результат просмотра и доступность БД/хранилища.

При удалении каждая попытка перечитывается под блокировкой товара. Недавно
возобновлённая загрузка пропускается; устаревшая незавершённая попытка получает
`CANCELLED` до удаления. После успешного удаления выставляется `stagingDeletedAt`.
Ошибку можно обработать повторным запуском. Проверяется точный префикс товара,
тип и UUID в ключе; постоянные артефакты не являются целями этой команды.

Удаление доступного владельцу неопубликованного черновика сначала подтверждает
транзакцию БД и лишь затем удаляет известные объекты. Полная сборка потерянных
постоянных артефактов не реализована; не нужно удалять их по возрасту.

В Docker-стадию `migrator` добавлены зависимости и файлы для запуска
`npx tsx scripts/cleanup-product-uploads.ts` с нужными переменными окружения/секретами.
Сборка и исполнение этого образа ещё требуют проверки на доступном Docker daemon.
В текущей сессии выполнялась только справка; очистка реальных объектов не запускалась.

## Lifecycle бакета: подготовленный образец

[ops/storage-staging-lifecycle.json](../ops/storage-staging-lifecycle.json) содержит
**отключённое** правило только для `staging/`: истечение через два дня, удаление
старых версий через два дня и отмена незавершённых multipart-загрузок через два дня.
Оно покрывает и временные объекты, журнал которых исчез вместе с черновиком.

Перед включением проверить, что в `staging/` нет постоянных файлов, учесть
настройки версионирования, объединить образец с действующими правилами бакета
и проверить на тестовом окружении. Не заменять существующую конфигурацию
одним образцом. Очистка по lifecycle асинхронная; точное время удаления не гарантируется.
Старый префикс загрузки версий этим образцом не обслуживается.

Образец не применялся. Синтаксис и порядок настройки сверены с документацией
[жизненного цикла Yandex Object Storage](https://yandex.cloud/ru/docs/storage/operations/buckets/lifecycles)
и [конфигурации правил S3 API](https://yandex.cloud/ru/docs/storage/s3/api-ref/lifecycles/xml-config).
