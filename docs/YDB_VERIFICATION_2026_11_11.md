# Повторная проверка YDB — 11 ноября 2026 года

Проверка выполнена с локального компьютера по просьбе пользователя после сообщения
о восстановлении базы. **Ранее воспроизводившийся таймаут SQL не повторился.**
Причина прежней ошибки и изменения на стороне облака в этой сессии не устанавливались.

## Что проверено на настоящей YDB

Команда `npx tsx scripts/ydb/verify.ts --write-probe` прошла все 11 проверок:

1. `SELECT 1` через нативный SDK.
2. Три последовательных SQL-чтения `CyberPolkaConnectionProbe`, которые раньше зависали.
3. Чтение журнала миграций и наличие исходных таблиц.
4. Колонки, первичные ключи и индексы `User`, `Product`, `Purchase`.
5. Чтение по первичному ключу через адаптер проекта и завершение транзакции.
6. Индексный поиск пользователя по синтетическому email.
7. Фильтрация массива `techStack`, статуса и ограниченная выдача продуктов.
8. Счётчик покупок с фильтром по индексу покупателя.
9. Запись диагностической строки, коммит и чтение с параметрами.
10. Откат транзакции: изменение первой строки отменилось, вторая не появилась.
11. Два параллельных увеличения значения в serializable-транзакциях: итог `2`,
    оба изменения сохранены.

Простые группы чтения заняли около 0,1–0,25 секунды, конкурентная проверка —
около 4,6 секунды. Это разовая функциональная проверка, не нагрузочное измерение.

Запись выполнялась только по двум случайным идентификаторам в существующей
`CyberPolkaConnectionProbe`. После проверки адресное удаление и повторное чтение
подтвердили **0 оставшихся диагностических строк**. Бизнес-таблицы только читались;
для запросов к данным использовались отсутствующие синтетические идентификаторы.

Отдельная проверка через официальный CLI также прошла:

```sql
SELECT COUNT(*) AS diagnostic_rows FROM `CyberPolkaConnectionProbe`;
SELECT COUNT(*) AS migration_records FROM `_SchemaMigration`;
```

Результаты: `diagnostic_rows = 0`, `migration_records = 1`.

## Состояние схемы и приложения

- В журнале применён только `001_baseline`, его хеш совпадает с исходным снимком.
- Найдены 33 исходные таблицы приложения; новые миграции 002–007 ожидают применения.
- Дополнительные таблицы пользователя, включая `testtable`, не изменялись.
- Новые миграции, импорт данных и полная интеграционная программа `ydb:test`
  в этой проверке не запускались.
- `DB_PROVIDER` остаётся PostgreSQL по умолчанию; сайт не переключён на YDB.
- Локальные `.env.local`, `.env`, `docker-compose.yml` и `docker-compose.ydb.yml`
  сверены по SHA-256 до/после проверки и не менялись. Ключ не выводился и не копировался.
- Лимиты RU, биллинг, права сервисного аккаунта и настройки облака не менялись.

Для повторения только чтения: `npx tsx scripts/ydb/verify.ts`.
Флаг `--write-probe` явно включает описанную проверку диагностической записи;
при ошибке очистки скрипт выводит только два точных идентификатора для сверки.
Он не создаёт таблицы и не переключает провайдер приложения.

## Что ещё не подтверждено

Полная работоспособность магазина и биржи на YDB потребует миграций 002–007,
нативных проверок связанных записей и бизнес-транзакций, а затем проверки
авторизованных сценариев приложения. Также предстоят проверка переноса старых
данных, резервного восстановления, файлов и внешних провайдеров.
Успех этих базовых проверок позволяет продолжать подготовку без окончательного
перехода рабочего сайта.
