## 1. Критичные блокеры

### 1.1. IP-allowlist вебхука ЮKassa не сработает на проде ⛔

**Файл:** `src/app/api/payment/webhook/route.ts`

**Проблема A — отдельные IP вместо диапазонов.**
Сейчас allowlist — это `Set` из одиночных адресов:

```ts
const YOOKASSA_IPS = new Set([
  "185.71.76.0", "185.71.76.1", ...
])
```

ЮKassa шлёт уведомления из **CIDR-диапазонов** (вида `185.71.76.0/27`,
`77.75.154.128/25` и т.д. — сверить актуальный список в документации ЮKassa,
раздел Webhooks → Безопасность). Реальный вебхук придёт, например,
с `185.71.76.28`, получит 403 — и **ни одна покупка не перейдёт в PAID**.
На тестовых платежах баг можно не заметить, если проверять статус вручную
через re-fetch.

**Проблема B — заголовок X-Forwarded-For спуфится.**
Nginx из `DEPLOY.md` проставляет `$proxy_add_x_forwarded_for` — он **дописывает**
реальный IP к заголовку, присланному клиентом. Код берёт первый элемент:

```ts
req.headers.get("x-forwarded-for")?.split(",")[0]   // ← подконтролен атакующему
```

Атакующий шлёт `X-Forwarded-For: 185.71.76.1` — и проходит allowlist.
В связке с тем, что метаданные всё же берутся из re-fetch, прямого увода денег
нет, но защитный слой фиктивен.

**Как исправить:**

1. В nginx передавать доверенный адрес отдельным заголовком:

```nginx
proxy_set_header X-Real-IP $remote_addr;
```

2. В коде проверять `X-Real-IP` (или последний элемент `X-Forwarded-For`)
   и сравнивать по CIDR:

```ts
// src/lib/ip.ts
function ipToLong(ip: string): number {
  return ip.split(".").reduce((acc, oct) => (acc << 8) + Number(oct), 0) >>> 0
}

export function ipInCidr(ip: string, cidr: string): boolean {
  const [range, bitsStr] = cidr.split("/")
  const bits = Number(bitsStr ?? 32)
  const mask = bits === 0 ? 0 : (~0 << (32 - bits)) >>> 0
  return (ipToLong(ip) & mask) === (ipToLong(range) & mask)
}
```

```ts
// webhook/route.ts — список сверить с актуальной документацией ЮKassa
const YOOKASSA_CIDRS = [
  "185.71.76.0/27",
  "185.71.77.0/27",
  "77.75.153.0/25",
  "77.75.156.11/32",
  "77.75.156.35/32",
  "77.75.154.128/25",
]

const clientIp = req.headers.get("x-real-ip")?.trim() ?? ""
const allowed = YOOKASSA_CIDRS.some((cidr) => ipInCidr(clientIp, cidr))
if (!allowed) return new Response("Forbidden", { status: 403 })
```

3. IPv6-диапазон ЮKassa (`2a02:5180::/32`) либо тоже поддержать, либо
   принудительно отдавать ей IPv4-эндпоинт (не публиковать AAAA-запись).

4. Тот же фикс источника IP применить в `src/proxy.ts` — rate limiting сейчас
   тоже обходится подменой `X-Forwarded-For`.

### 1.2. Бэкапов нет вообще ⛔

Ни в `DEPLOY.md`, ни в скриптах нет ни слова про резервное копирование.
Для платформы с деньгами, эскроу и балансами разработчиков потеря БД =
потеря бизнеса.

**Минимальное решение — ночной pg_dump в S3:**

```bash
# /opt/polka/scripts/backup.sh
#!/usr/bin/env bash
set -euo pipefail

STAMP=$(date +%Y-%m-%d_%H%M)
FILE="/tmp/polka_${STAMP}.sql.gz"

docker compose -f /opt/polka/docker-compose.yml exec -T db \
  pg_dump -U polka polka_db | gzip > "$FILE"

# отдельный бакет, не polka-files; настроить lifecycle на 30 дней
aws s3 cp "$FILE" "s3://polka-backups/db/" \
  --endpoint-url https://storage.yandexcloud.net

rm -f "$FILE"
```

```cron
# crontab -e (на сервере)
0 3 * * * /opt/polka/scripts/backup.sh >> /var/log/polka-backup.log 2>&1
```

**Обязательно:**
- [ ] Отдельный бакет `polka-backups` с отдельным сервисным аккаунтом
      (ключи от `polka-files` не должны иметь доступа к бэкапам — защита
      от сценария «утекли ключи приложения → стёрли и данные, и бэкапы»).
- [ ] **Один проверенный вручную restore до запуска.** Бэкап, который ни разу
      не разворачивали, — это не бэкап.
- [ ] Включить versioning на бакете `polka-files` (защита файлов продуктов
      от случайного удаления/перезаписи).
- [ ] Алерт, если бэкап не появился за сутки (хотя бы скрипт-проверка + Telegram).

### 1.3. Cron для эскроу и AI-ревью не настроен ⛔

Пункт из `ROADMAP.md` («Системный cron для эскроу — добавить в crontab сервера»)
не закрыт, `deploy.sh` crontab не трогает. Последствия:

- `/api/cron/escrow` не вызывается → **деньги разработчикам никогда
  не разблокируются**, статусы Purchase не переходят в DELIVERED;
- `/api/cron/ai-review` не вызывается → оплаченные AI-ревью висят
  в PROCESSING вечно (покупатель заплатил ₽390 и ничего не получил).

**Как исправить:**

```cron
# crontab -e (на сервере); CRON_SECRET — тот же, что в .env
0 * * * *   curl -fsS -H "x-cron-secret: $CRON_SECRET" https://your-domain.com/api/cron/escrow    >> /var/log/polka-cron.log 2>&1
*/5 * * * * curl -fsS -H "x-cron-secret: $CRON_SECRET" https://your-domain.com/api/cron/ai-review >> /var/log/polka-cron.log 2>&1
```

- [ ] Добавить установку crontab в `deploy.sh` или в раздел DEPLOY.md
      «первичная настройка сервера» — чтобы шаг нельзя было забыть.
- [ ] В чеклист после деплоя добавить проверку: «cron отработал, в логе
      есть успешный вызов обоих эндпоинтов».
- [ ] Алерт в Sentry, если cron-эндпоинт не вызывался > N часов
      (например, писать timestamp последнего запуска в БД и проверять).

### 1.4. Seed-аккаунты с известными паролями могут попасть на прод ⛔

`DEPLOY.md` предлагает при первом запуске:

```bash
docker exec polka npm run db:seed   # только для первичного сида
```

Сид создаёт `admin@polka.test / password123`, `moderator@polka.test /
password123` и т.д. Если выполнить это на проде — на площадке появляется
**админ с публично задокументированным паролем**. В чеклисте после деплоя
пункта о тестовых учётках нет.

**Как исправить:**

1. Разделить сиды:
   - `prisma/seed.ts` → только справочные данные (категории и т.п.), безопасен для прода;
   - `scripts/seed-demo.ts` → демо-продукты и тестовые пользователи, **только dev**.
2. Защита от случайного запуска в самом скрипте:

```ts
if (process.env.NODE_ENV === "production" && !process.env.ALLOW_DEMO_SEED) {
  throw new Error("Demo seed запрещён в production")
}
```

3. Создание реального админа — отдельным скриптом с паролем из аргумента/env:

```bash
npx tsx scripts/create-admin.ts --email admin@polka.app
```

4. В чеклист после деплоя: «в таблице User нет аккаунтов `*@polka.test`».

## 2. Важно до первых живых пользователей

### 2.1. Юридический контур отсутствует (152-ФЗ + требования ЮKassa)

В проекте не найдено: публичной оферты, политики конфиденциальности,
пользовательского соглашения, согласия на обработку персональных данных.

Почему это не «потом»:
- ЮKassa при модерации боевого магазина, как правило, требует наличие
  оферты и реквизитов на сайте — без этого могут не выдать боевой `shopId`;
- сбор email/телефона/имени без согласия и политики — прямое нарушение 152-ФЗ;
- эскроу, споры и возвраты без оферты юридически не на что опереть.

**Как исправить:**
- [ ] Страницы `/legal/offer`, `/legal/privacy`, `/legal/terms`
      (статичные Server Components, ссылки в футере).
- [ ] Чекбокс при регистрации: «Принимаю условия соглашения и даю согласие
      на обработку персональных данных» + проверка на бэкенде
      в `POST /api/auth/register`.
- [ ] Реквизиты ИП/ООО в футере (требование ЮKassa).
- [ ] Тексты — у юриста или хотя бы адаптированный шаблон под модель
      «площадка-агент»; шаблонные документы «интернет-магазина» не подходят,
      т.к. ПОЛКА — посредник между разработчиком и покупателем.

### 2.2. Нет восстановления пароля

Есть только смена пароля в настройках (`/api/settings/password`) — для уже
залогиненного. Забыл пароль → доступ к оплаченным покупкам потерян,
ручная работа поддержки. SMTP уже настроен, добавить flow недорого.

**Как исправить:**
- [ ] Модель `PasswordResetToken` (или поля `resetToken`/`resetTokenExpiresAt`
      в User): хэш токена + TTL 1 час, одноразовость.
- [ ] `POST /api/auth/forgot` — всегда отвечает 200 («если аккаунт существует,
      письмо отправлено»), чтобы не раскрывать наличие email в базе;
      rate limit 3/час на IP и на email.
- [ ] `POST /api/auth/reset` — проверка токена, установка нового пароля,
      инвалидация токена и всех сессий.
- [ ] Страницы `/forgot` и `/reset/[token]`, ссылка «Забыли пароль?» на `/login`.

### 2.3. Postgres торчит наружу со слабым паролем

В `docker-compose.yml` у сервиса `db` проброшен порт `5432:5432` и пароль
`password`. На сервере это означает Postgres, доступный из интернета
(если не закрыт firewall'ом).

**Как исправить:**
- [ ] Убрать `ports` у `db` в прод-конфигурации — внутри compose-сети
      приложение достучится по имени `db` без проброса. Для локального
      доступа к БД использовать `docker compose exec db psql` или SSH-туннель.
- [ ] Сменить пароль на случайный (`openssl rand -base64 24`), вынести
      в `.env`, обновить `DATABASE_URL`.
- [ ] Подстраховка на уровне сервера: `ufw allow 22,80,443/tcp && ufw enable`.

### 2.4. Нет health-эндпоинта и healthcheck в compose

`deploy.sh` обещает zero-downtime restart, но без healthcheck новый контейнер
получает трафик до фактической готовности (миграции, прогрев, коннект к БД).
Также нечего дёргать внешнему uptime-мониторингу: Sentry ловит ошибки,
но не «сайт лежит целиком».

**Как исправить:**

```ts
// src/app/api/health/route.ts
import { db } from "@/lib/db"

export async function GET() {
  try {
    await db.$queryRaw`SELECT 1`
    return Response.json({ ok: true })
  } catch {
    return Response.json({ ok: false }, { status: 503 })
  }
}
```

```yaml
# docker-compose.yml
services:
  app:
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3000/api/health"]
      interval: 15s
      timeout: 5s
      retries: 3
      start_period: 30s
  db:
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U polka -d polka_db"]
      interval: 10s
      timeout: 5s
      retries: 5
```

- [ ] `depends_on: { db: { condition: service_healthy } }` у `app`.
- [ ] Подключить внешний uptime-мониторинг (UptimeRobot / Betterstack)
      на `/api/health` с алертом в Telegram.

### 2.5. Нет security-заголовков

Ни в `next.config.ts`, ни в nginx-конфиге из DEPLOY.md нет HSTS,
X-Frame-Options, X-Content-Type-Options, Referrer-Policy.

**Как исправить (nginx, server-блок 443):**

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Frame-Options "DENY" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Permissions-Policy "camera=(), microphone=(), geolocation=()" always;
```

CSP — отдельной задачей после запуска: с Next.js (inline-скрипты, Telegram
Login Widget) её нужно собирать аккуратно, через `Content-Security-Policy-Report-Only`
сначала.

## 3. Можно после запуска

### 3.1. Rate limiter — в памяти процесса

`src/lib/ratelimit.ts` честно задокументирован: при нескольких инстансах
лимиты перестанут работать глобально. Для одного сервера — нормально.

- [ ] При горизонтальном масштабировании → Redis (`@upstash/ratelimit`).
- [ ] Мелкая нестыковка уже сейчас: `limits.payment` объявлен с ключом
      `userId`, а в `src/proxy.ts` передаётся IP. Привести к одному —
      для платежей лучше userId (берётся из сессии в самом route handler).
- [ ] После фикса 1.1 убедиться, что источник IP для лимитера тоже
      `X-Real-IP`, а не первый элемент `X-Forwarded-For`.

### 3.2. Нет email-верификации при регистрации

Регистрация сразу логинит пользователя без подтверждения почты. Риски:
спам-аккаунты, отзывы/вопросы с одноразовых адресов, чужой email в аккаунте.
Для MVP допустимо, но:

- [ ] Добавить `emailVerified` (поле уже стандартно для NextAuth) + письмо
      с токеном; неверифицированным ограничить публикацию отзывов и вопросов.

### 3.3. Процесс выплат разработчикам не формализован

`POST /api/payouts` создаёт запрос на вывод, но сам перевод денег, судя
по коду, исполняется вручную. Для старта это нормально, но:

- [ ] Зафиксировать в админке статусы (REQUESTED → PROCESSING → PAID / REJECTED)
      и SLA («выплаты по вторникам и пятницам») — и написать это в FAQ `/sell`,
      чтобы не плодить обращения «где мои деньги».
- [ ] Двойная проверка суммы: запрошено ≤ доступный баланс **на момент
      исполнения**, а не только на момент запроса (между ними мог пройти возврат).
